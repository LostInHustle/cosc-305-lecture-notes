# Lecture Notes: Project Scope Management

## 1. Introduction to Scope Planning

This lecture focuses on project scope management, which is one of the main parts of project planning.

Earlier planning activities establish how the project will be managed. Scope planning moves into the core details of the project by defining what work must be completed, who will complete it, and what results must be delivered.

A clear scope helps everyone understand the project in the same way. It reduces confusion between the project team, client, sponsor, users, and other stakeholders.

## 2. Project Scope Management Processes

Project scope management contains six major processes.

The first four processes happen during the planning phase:

1. Plan scope management
2. Collect requirements
3. Define scope
4. Create the Work Breakdown Structure, also called the WBS

The final two processes happen during project monitoring and control:

5. Validate scope
6. Control scope

These processes are connected. The output from one process often becomes an input for another process.

## 3. Thinking of Scope Planning as a Process

Each scope activity can be understood by asking four questions:

1. What information is needed as an input?
2. What is the purpose of the activity?
3. What work must be completed?
4. What output should be produced?

For example, requirements are an important input for defining the scope. Once the requirements are understood, the project team can create a scope statement and a WBS.

## 4. Why Scope Management Is Important

Scope management defines what the project will and will not include.

A clear scope answers questions such as:

1. What product, service, or result will be created?
2. What features will be included?
3. What work will the project team complete?
4. What work will the client complete?
5. What documents will be delivered?
6. How will success be measured?
7. What is explicitly excluded?

Unclear scope is a common reason for project failure. The client may expect one result while the project team develops something different. This problem might not become obvious until the final product is delivered.

A well defined scope creates a shared understanding before major work begins.

## 5. Example of Project Scope

Imagine that a business wants a website to display its products.

Possible items included in the scope are:

1. Customers can view a list of products.
2. Customers can search for products.
3. Customers can view product descriptions.
4. Customers can view product images.

Possible items excluded from the scope are:

1. Customers cannot purchase products through the website.
2. The project team will not enter all product information.
3. The client must upload and maintain its own product information.
4. The project will not process online payments.

These exclusions are important because they prevent different expectations at the end of the project.

## 6. Scope Deliverables

Scope planning should identify every tangible result that the project team will provide.

Deliverables may include:

1. The final product or service
2. Project plans
3. Schedules
4. Budget documents
5. Designs
6. Blueprints
7. Technical documents
8. Training materials
9. Test results
10. User guides
11. Models or prototypes

Documents should be listed as deliverables if the client expects to receive them. Some organizations may provide only the final product unless the supporting documents are explicitly included in the agreement.

## 7. Writing Measurable Scope Statements

Scope statements and requirements should be specific and measurable.

Vague statements make it difficult to decide whether the project has succeeded. Measurable statements provide clear acceptance criteria.

### Example One

Weak statement:

A new registration system will be created.

Improved statement:

Students will be able to register for classes using a web browser or smartphone.

The improved version explains what users will be able to do and how they will access the system.

### Example Two

Weak statement:

The system will be fast.

Improved statement:

The system response time will be less than one second.

The improved version includes a measurable performance target.

### Example Three

Weak statement:

The system will support the required number of users.

Improved statement:

Seventy five students must be able to add an average of three classes during each fifteen minute period.

The improved version identifies a measurable volume and time period.

### Example Four

Weak statement:

Users will be happy with the system.

Improved statement:

User satisfaction will be measured using a standard survey, and the average score must be at least five on a seven point scale.

The improved version explains how satisfaction will be tested and what result will be considered acceptable.

## 8. Requirements as an Input to Scope

Requirements describe what stakeholders need from the project.

The project team must collect requirements before it can accurately define the scope. The logic is simple:

1. Meet with stakeholders.
2. Identify their needs.
3. Record those needs as requirements.
4. Clarify unclear requirements.
5. Add measures and acceptance criteria.
6. Prioritize the requirements.
7. Use the requirements to define the project scope.

Requirements can be grouped into several categories.

## 9. Functional Requirements

Functional requirements describe what the system must do.

They often describe actions that users can perform or services that the system must provide.

Examples include:

1. Students can register for courses.
2. Students can view available courses.
3. Students can monitor their registration status.
4. Students can pay their fees.
5. The system can store customer orders.
6. The system can send registration confirmations.
7. Event organizers can view a list of registered participants.

A useful question is:

What can the user or system do?

## 10. Nonfunctional Requirements

Nonfunctional requirements describe how well the system must operate.

They may address performance, availability, usability, reliability, security, capacity, or quality.

Examples include:

1. The system must respond within one second.
2. The system must be available for a specified number of hours each day.
3. The database must store a specified number of records.
4. The system must restart within a specified amount of time after a failure.
5. The system must support a certain number of simultaneous users.
6. The system must achieve a specified user satisfaction score.

A useful question is:

How well must the system perform?

## 11. Development Requirements

Development requirements describe project constraints related to creating the solution.

Examples include:

1. The project must be completed within four weeks.
2. The project must remain within the approved budget.
3. The team has a limited number of staff members.
4. The solution must meet a defined quality level.
5. The team has a maximum number of available effort units.

These requirements affect what the team can realistically deliver.

## 12. Technical Requirements

Technical requirements identify specific technologies, platforms, tools, or integrations that must be used.

Examples include:

1. The system must use a specified programming language.
2. The project must use a database for which the organization already owns a licence.
3. The solution must connect to an existing enterprise system.
4. The system must work with the organization’s current technical environment.
5. The project must follow an approved technical architecture.

Technical requirements may be based on existing licences, staff skills, compatibility needs, or organizational standards.

## 13. Business Requirements

Business requirements explain why the project is needed from the organization’s perspective.

Examples include:

1. Reduce registration processing time.
2. Improve customer access to product information.
3. Support an organizational strategy.
4. Reduce operating costs.
5. Improve service quality.
6. Increase the number of users who can access a service.

Business requirements connect the project to a larger organizational need.

## 14. User Requirements

User requirements describe what users expect from the final product.

Examples include:

1. Students can register using a browser.
2. Users can view their registration status.
3. Organizers can see who has registered.
4. Users receive confirmation after successful registration.
5. Users can cancel a registration before a specified deadline.

User requirements should be written from the perspective of the people who will use the system.

## 15. Regulatory Requirements

Regulatory requirements describe laws, policies, regulations, or standards that the project must follow.

Examples include:

1. Privacy requirements
2. Security standards
3. Accessibility standards
4. Industry regulations
5. Data retention rules
6. Organizational policies

These requirements may be mandatory even if users do not directly request them.

## 16. Measuring Requirements

Every major requirement should have a suitable measurement.

Different requirements require different measurement methods.

Examples include:

1. System size can be measured using storage capacity.
2. Performance can be measured using response time.
3. Capacity can be measured using the number of users or records.
4. Availability can be measured using operating hours or percentage of available time.
5. Reliability can be measured using the rate of failures.
6. Robustness can be measured using restart or recovery time.
7. Usability can be measured using user testing or surveys.
8. User satisfaction can be measured using a rating scale.
9. Quality can be measured using the number of defects.
10. Completion can be measured using approved acceptance criteria.

A requirement such as easy to use is too vague by itself. It should be connected to a test, survey, task completion rate, or another clear measure.

## 17. Techniques for Collecting Requirements

Requirements are usually collected by communicating with stakeholders.

Common techniques include:

1. Stakeholder meetings
2. Individual interviews
3. Focus groups
4. Brainstorming sessions
5. Workshops
6. Observation
7. Surveys
8. Prototypes
9. Document reviews
10. Group creativity activities

Prototypes can be especially useful because stakeholders may find it easier to react to a visible example than to explain everything verbally.

## 18. Sources of Requirements

Requirements may come from many different sources.

Possible sources include:

1. Project sponsors
2. Clients
3. Customers
4. End users
5. Project managers
6. Technical specialists
7. Quality specialists
8. Suppliers
9. Competitors
10. Existing project documents
11. Organizational plans
12. Government regulations
13. Industry standards

Each group may have a different perspective. The project team must combine these perspectives into a realistic and consistent set of requirements.

## 19. Discussing Cost and Scope with Stakeholders

Stakeholders often request more features than the available time and budget can support.

The project team should explain how changes in scope affect:

1. Cost
2. Time
3. Resources
4. Quality
5. Technical complexity
6. Project risk

For example, a basic website that only displays products may cost a certain amount. Adding online ordering, account management, and payment processing could significantly increase the cost and development time.

The goal is to reach a realistic agreement that provides value to the client and remains achievable for the project team.

## 20. Requirements Traceability Matrix

After requirements are collected, they should be recorded in a requirements traceability matrix.

A requirements traceability matrix commonly includes:

1. Requirement identification code
2. Requirement description
3. Requirement source
4. Priority
5. Current status
6. Acceptance criteria
7. Related deliverable
8. Responsible person
9. Test result
10. Completion status

The matrix connects each requirement to its source and tracks it throughout the project.

## 21. Why Traceability Matters

The source of each requirement should be recorded so the team knows whom to contact when clarification is needed.

This is useful when:

1. A requirement is unclear.
2. A requirement becomes too expensive.
3. A proposed feature is not technically feasible.
4. A stakeholder requests a change.
5. Two requirements conflict.
6. The team needs approval for a different solution.

Priority is also important. High priority requirements should usually receive attention before lower priority requirements.

Status allows the team to monitor progress and identify requirements that have been forgotten or delayed.

Even obvious requirements should be recorded. During a busy project, the team may focus on complex details and accidentally overlook a basic feature.

## 22. Work Breakdown Structure

After requirements and scope have been defined, the team creates a Work Breakdown Structure.

The Work Breakdown Structure is commonly abbreviated as WBS.

A WBS divides the total project work into smaller and more manageable components.

The general process is:

1. Begin with the main project objective.
2. Divide the objective into major deliverables or areas of work.
3. Divide each area into smaller activities.
4. Continue dividing until the work is manageable.
5. Assign codes or numbers to each component.
6. Confirm that all required work is included.

## 23. Simple WBS Example

Suppose the main objective is to clean a room.

The work could be divided into these major activities:

1. Remove objects from the floor.
2. Vacuum the floor.
3. Mop the floor.
4. Clean the furniture.
5. Organize the remaining items.

Each major activity can be divided into smaller tasks.

For example, cleaning the furniture may include:

1. Dust the desk.
2. Wipe the shelves.
3. Clean the chair.
4. Organize objects on the desk.

The same idea applies to larger projects. A complex system may contain several major components, and each component may contain many smaller tasks.

## 24. Guidelines for Creating a WBS

A useful WBS should follow these guidelines:

1. Begin with the full project objective.
2. Divide work into logical components.
3. Continue dividing large tasks into smaller tasks.
4. Stop when each task is manageable.
5. Give each task a clear name.
6. Use numbering or coding to show relationships.
7. Make sure smaller tasks combine to complete the larger task.
8. Make sure all major deliverables are covered.
9. Avoid including work that is outside the approved scope.
10. Update the WBS when approved changes affect the work.

Large projects may have several levels in the WBS. A major component may even operate like a smaller project within the larger project.

## 25. WBS Dictionary

The WBS dictionary explains the components in the WBS.

It may include:

1. A task identification code
2. A task description
3. The expected result
4. The responsible person
5. Required resources
6. Estimated time
7. Dependencies
8. Acceptance criteria
9. Related requirements
10. Important assumptions

The WBS shows the structure of the work, while the WBS dictionary provides details about each part.

## 26. Project Scope Statement

The project scope statement is a written description of what the project will deliver.

It may include:

1. Project purpose
2. Project objectives
3. Major deliverables
4. Included requirements
5. Explicit exclusions
6. Project constraints
7. Project assumptions
8. Acceptance criteria
9. Success measures
10. Important deadlines
11. Budget limits
12. Intended users

A scope statement should clearly explain:

1. What will be developed
2. Who will use it
3. What features will be included
4. What features will not be included
5. When it must be completed
6. What resource or budget limits apply
7. How the result will be accepted

## 27. Deliverables Compared with Requirements

A requirement describes a need or expected capability.

A deliverable is the actual product, service, component, or document provided by the project.

Example:

Requirement:

Students must be able to register for an event.

Deliverable:

A browser based event registration system.

Another example:

Requirement:

Administrators must be able to view registered students.

Deliverable:

An administrator registration report or participant management page.

Requirements describe what the solution must accomplish. Deliverables describe what the project team will provide.

## 28. Scope Baseline

The scope baseline is the approved version of the project scope.

It normally includes:

1. The project scope statement
2. The WBS
3. The WBS dictionary

The scope baseline becomes an important reference during project execution. Proposed changes can be compared with it to determine whether they affect the approved scope.

## 29. Inputs to Scope Planning

The project charter is one of the main inputs to scope planning.

The project charter comes from the initiation phase and usually contains:

1. The reason for the project
2. The general project objective
3. The proposed solution
4. Major stakeholders
5. Initial constraints
6. High level requirements
7. Initial assumptions

Other inputs can include:

1. Stakeholder needs
2. Organizational strategy
3. Existing project documents
4. Technical information
5. Policies and standards
6. Lessons from previous projects
7. Meetings and interviews
8. Available resources

## 30. Validating Scope

Scope validation occurs during monitoring and control.

Validation means reviewing completed deliverables with the client, sponsor, or authorized stakeholder to confirm that the work meets the agreed requirements and acceptance criteria.

The basic process is:

1. Complete a deliverable.
2. Compare it with the approved requirements.
3. Test it using the acceptance criteria.
4. Present it to the appropriate stakeholder.
5. Record feedback.
6. Obtain formal acceptance when the deliverable is satisfactory.

The result may be an accepted deliverable or a request for correction.

## 31. Controlling Scope

Controlling scope means monitoring the project scope and managing approved changes.

The project team should:

1. Monitor the status of each requirement.
2. Compare completed work with the scope baseline.
3. Identify requested changes.
4. Evaluate the effects of each change.
5. Discuss changes with the client or sponsor.
6. Obtain approval before changing the scope.
7. Update project documents.
8. Update the requirements traceability matrix.
9. Update the WBS if necessary.

Scope should not be changed informally. A small feature request may affect the schedule, budget, staffing, testing, and quality of the entire project.

## 32. Main Outputs of Scope Management

Important outputs include:

1. Scope management plan
2. Requirements management plan
3. Requirements documentation
4. Requirements traceability matrix
5. Project scope statement
6. Scope baseline
7. Work Breakdown Structure
8. WBS dictionary
9. Accepted deliverables
10. Change requests
11. Work performance information
12. Updated plans and project documents

## 33. Summary of the Scope Management Process

The complete process can be summarized as follows:

1. Plan how scope will be managed.
2. Collect requirements from stakeholders.
3. Categorize and measure the requirements.
4. Record requirements in a traceability matrix.
5. Define what is included and excluded.
6. Write the project scope statement.
7. Create the WBS.
8. Create the WBS dictionary.
9. Complete the planned work.
10. Validate completed deliverables.
11. Control scope and manage approved changes.

## 34. In Class Activity

Students work in groups of four.

Each group selects one of the available project scenarios from the assignment posted on Canvas.

Possible team roles include:

1. Project manager
2. Project sponsor
3. User representative
4. Technical lead
5. Requirements specialist
6. Quality specialist

Each member should take responsibility for a role.

The group should then:

1. Review the selected scenario.
2. Identify unclear requirements.
3. Ask the sponsor clarifying questions.
4. Make acceptance criteria measurable.
5. Prioritize the requirements.
6. Identify assumptions and constraints.
7. Write a scope statement.
8. Identify included deliverables.
9. Identify explicit exclusions.
10. Connect deliverables to requirement identification codes.
11. Create a simple WBS.
12. Complete the reflection section.
13. Share the completed document with all group members.
14. Have each student submit the document to Canvas.

## 35. Event Registration Scenario Discussion

One scenario involves a browser based event registration system.

Important questions for this scenario include:

1. Does registration mean creating an account or joining an event?
2. Can students cancel their event registration?
3. Is account deletion different from registration cancellation?
4. What is the registration deadline?
5. What is the cancellation deadline?
6. Can a student register more than once?
7. What happens when the event reaches eighty participants?
8. Will students receive confirmation after successful registration?
9. What message appears after a failed registration?
10. How will organizers verify who is authorized to attend?
11. Who will maintain the participant list?
12. Will test accounts be provided?
13. Is payment processing excluded because the event is free?
14. Is additional authentication required?
15. Who approves requirement changes?

These questions turn unclear ideas into testable requirements.

## 36. Possible Acceptance Criteria for the Scenario

Examples of measurable acceptance criteria include:

1. A student can register for the event using a supported browser.
2. The system prevents the same student from registering twice.
3. The system accepts no more than eighty active registrations.
4. A successful registration produces a confirmation message.
5. An unsuccessful registration produces an error message explaining the reason.
6. A student can cancel before the approved deadline.
7. Organizers can view the current participant list.
8. Only authorized organizers can access participant information.
9. The system records the time of each registration.
10. The completed system is delivered within four weeks.

## 37. Key Takeaways

1. Scope defines what the project includes and excludes.
2. Requirements are the foundation of scope.
3. Requirements should be specific, measurable, and traceable.
4. Different stakeholders provide different types of requirements.
5. Functional requirements describe what the system does.
6. Nonfunctional requirements describe how well it performs.
7. Deliverables are the actual results provided by the project.
8. The WBS divides the total project work into manageable components.
9. The scope statement, WBS, and WBS dictionary form the scope baseline.
10. Validation confirms that deliverables meet expectations.
11. Scope control manages changes throughout the project.
12. Clear scope reduces conflict, missed work, cost increases, and project failure.

## Final Study Tip

When reviewing a project scope, ask these questions:

1. What are we building?
2. Why are we building it?
3. Who will use it?
4. What must it do?
5. How well must it perform?
6. What is included?
7. What is excluded?
8. How will success be measured?
9. What work must be completed?
10. Who must approve the final result?

If these questions have clear and measurable answers, the project scope is likely well defined.
